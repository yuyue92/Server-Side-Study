# 医院内部排班系统 — 设计方案

## 一、整体架构思路

系统本质是一个**约束满足问题（CSP, Constraint Satisfaction Problem）**，核心是在时间、人员、资质、规则四个维度之间找到合法且公平的分配方案。

---

## 二、数据模型设计

### 核心实体关系

```
人员（Staff）
  ├── 基本信息（工号、姓名、科室、职称）
  ├── 资质标签（Qualifications）：如"ICU认证"、"儿科执照"
  └── 工时账户（WorkloadAccount）：累计工时、本月工时、连续值班天数

科室（Department）
  └── 岗位需求模板（ShiftTemplate）：每个班次需要哪些资质、几人

班次定义（ShiftType）
  ├── 早班 08:00-16:00
  ├── 晚班 16:00-00:00
  └── 夜班 00:00-08:00

时间片（Slot）
  ├── 科室 + 日期 + 班次类型
  ├── 所需人数 & 所需资质
  └── 状态：空缺 / 已排 / 锁定

排班记录（Assignment）
  ├── Staff → Slot 的映射
  ├── 创建类型：系统自动 / 手动 / 应急
  └── 审核状态：待审 / 生效 / 撤销

换班申请（SwapRequest）
  ├── 发起人 + 目标班次
  ├── 接替人（指定或系统推荐）
  └── 状态流转：申请 → 规则校验 → 主任审批 → 生效
```

## 三、规则引擎设计（最核心）

### 设计原则：规则分层 + 可配置

将规则分为两类，优先级明确：

```
硬规则 Hard Rules（必须满足，违反直接拒绝）
│
├── H1: 同一人同一时间段不能有两个班次（物理冲突）
├── H2: 班次所需资质必须完全匹配
├── H3: 连续工作时长不超过 N 小时（法规红线，如24h）
├── H4: 两班之间必须有最低休息间隔（如8h）
└── H5: 某些班次人数不得低于安全下限

软规则 Soft Rules（尽量满足，违反给出警告或影响评分）
│
├── S1: 每周休息天数不少于 N 天
├── S2: 夜班连续不超过 M 天
├── S3: 同科室人员公平轮转（工时差不超过阈值）
├── S4: 医生本人休假申请优先尊重
└── S5: 节假日补偿性安排
```

### 规则引擎执行流程

```
新增排班请求
      ↓
① 提取上下文（该人的历史Assignment、当前周期工时）
      ↓
② 逐条执行 Hard Rules → 任一失败 → 拒绝 + 返回具体原因
      ↓
③ 逐条执行 Soft Rules → 计算违规惩罚分
      ↓
④ 综合评分 → 通过（带警告）或 建议替代方案
```

规则以**接口形式**定义，每条规则是一个独立的校验器，便于后续增删改，不影响其他规则。

## 四、自动排班算法思路

手动排班适合小规模调整，大规模周期性排班（如月度排班）需要算法辅助。

### 推荐方案：贪心 + 回溯

**第一步：预处理**
- 统计每位医护人员当前的累计工时、连续班次数
- 按"欠班"程度排序（工时越少的优先分配）

**第二步：Slot遍历分配**
- 按时间顺序遍历所有待排Slot
- 对每个Slot，筛选出**合资质 + 通过Hard Rules**的候选人
- 在候选人中优先选择**综合评分最低**（工时最少、最久未排夜班等）的人

**第三步：冲突回溯**
- 若某个Slot无法找到合法候选人，触发回溯，调整前序排班
- 回溯深度可配置，超出则标记该Slot为"待人工处理"

**公平性保障**：引入一个**工时平衡系数**，让评分函数天然倾向于选择累计工时较少的人，避免长期劳逸不均。

## 五、应急调度模块

应急场景的特点：**时间紧、约束可适当放松（软规则）**。

### 流程设计

```
触发应急（某人临时请假/生病）
      ↓
① 找出受影响的 Slot
      ↓
② 快速候选人筛选：
   - 必须通过 Hard Rules（资质、冲突）
   - 软规则适当放宽（如连续班次限制从3天放至4天）
      ↓
③ 按优先级推荐候选人：
   - 优先：当天休班且工时偏少的人
   - 次选：可调换班次的人（A换B、B顶空缺）
      ↓
④ 推送通知 → 人工一键确认 → 生效
      ↓
⑤ 记录"应急标记"，用于后续公平性补偿计算
```

## 六、SQLite 数据库设计要点

SQLite 轻量、无服务器，适合单机部署的内部系统。关键设计点：

**使用事务保证一致性**：排班写入 + 工时更新 + 规则日志，必须在同一事务内完成，要么全成功，要么全回滚。

**索引策略**：
- `assignments(staff_id, date)` — 快速查询某人某天的排班
- `assignments(slot_id, status)` — 快速检查某Slot是否已满员
- `staff(department_id, qualification)` — 快速筛选候选人

**审计日志表**：所有排班变更（创建、修改、撤销）都写入独立的 `audit_log` 表，字段包括操作人、时间、变更前后的快照，满足医院合规要求。

## 七、Go 服务层设计

```
cmd/
  └── server/         # 入口，HTTP服务启动

internal/
  ├── domain/         # 核心领域模型（Staff, Slot, Assignment等纯结构体）
  ├── rules/          # 规则引擎（每条规则一个文件，实现Rule接口）
  ├── scheduler/      # 自动排班算法
  ├── repository/     # SQLite数据访问层（DAO）
  ├── service/        # 业务逻辑编排
  └── api/            # HTTP Handler（REST接口）
```

核心接口约定：
- `Rule` 接口：`Validate(ctx, assignment) → (passed bool, reason string)`
- `RuleEngine`：持有所有Rule列表，串行执行，聚合结果
- `Scheduler`：调用RuleEngine + Repository，输出排班方案

## 八、关键难点与应对

| 难点 | 应对策略 |
|------|----------|
| 规则组合爆炸 | 硬规则优先剪枝，大幅减少软规则计算量 |
| 排班无解（人手不足） | 明确标记缺口，而非静默失败；输出缺口报告 |
| 公平性量化 | 引入"工时偏差率"指标，可视化展示各人工时分布 |
| 规则频繁变更 | 规则参数（如连续班次上限）存入配置表，无需改代码 |
| SQLite并发 | WAL模式 + 写操作串行化，适合内部单机部署场景 |

---

## 总结

整个系统的核心链路是：**规则引擎校验 → 评分函数排序 → 事务写入 → 审计记录**。把规则引擎做成可插拔的接口设计，是后期维护和扩展的关键。算法层面不需要追求最优解，**"足够好 + 快速"的贪心方案**在实际排班场景中反而比精确算法更实用，因为最终都需要人工审核兜底。
